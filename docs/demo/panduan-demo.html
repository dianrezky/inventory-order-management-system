Maksud kedua kalimat di atas (terverifikasi di kode)

1. "Redis mati → beralih ke file, login tetap jalan"

  • Sesi = data "siapa yang sedang login" (user_id, role, last_activity) di sisi server; browser hanya memegang cookie berisi ID acak. Normalnya disimpan di Redis (cepat, kedaluwarsa otomatis 3600 dtk, tidak membebani MySQL). Hanya sesi di Redis — bukan data bisnis/stok.
  • Tiap request, SessionManager mengecek koneksi ke Redis (timeout 0,5 dtk). Gagal → tulis peringatan di log dan pakai sesi berbasis file (session.save_handler=files). Tanpa ini, Redis mati membuat semua request gagal/menggantung dan tak ada yang bisa login. Sudah diuji: dengan Redis palsu, sesi tetap aktif di mode file.
  • Batasan jujur (inferensi dari kode): sesi lama tidak ikut pindah, jadi pengguna yang sudah login harus login ulang saat Redis mati; login baru bisa, tapi sesinya tersimpan di file lokal.

2. "Password dicek dengan bcrypt, tidak pernah disimpan polos"

  • Saat user dibuat/ganti password: password_hash($pw, PASSWORD_BCRYPT) → di DB hanya hash $2y$10$… (60 karakter, salt acak, sengaja lambat). Password asli tidak ada di DB, sesi, maupun log.
  • Saat login: password_verify($pw, hash) — hash tidak bisa "dibalik"; dibandingkan, bukan didekripsi. Salah/akun nonaktif/email tak dikenal → pesan sama.
Versi lebih lengkap: Lampiran A.

Soal cache Memcached — data apa tepatnya? Angka dashboard (nilai inventori, low stock, jumlah PO/SO, antrean) dibaca langsung dari MySQL tiap halaman dibuka (badge "LIVE SYNCED") — tidak di-cache. Yang di-cache Memcached hanya dua hal (izin role dipindah ke Redis, lihat bawah tabel):
KeyIsiTTLInvalidasi
product:<SKU>Satu produk per SKU (dipakai API /api/products/{sku}/availability); bukan stok5 menitDihapus saat produk diubah / dinonaktifkan / diaktifkan
file_validation.rulesAturan tipe gambar upload produk1 jamHanya kedaluwarsa TTL
Stok tidak pernah di-cache (selalu MySQL + SELECT … FOR UPDATE) agar anti-oversell tak bergantung data usang. Bila Memcached mati, aplikasi tetap jalan penuh dari MySQL. Tabel izin role (role_permissions.grouped, 1 jam) kini di-cache di Redis (database terpisah dari sesi), bukan Memcached. Versi lengkap: Lampiran B.

LAMPIRAN ASesi, Redis fallback, dan bcrypt

Menjabarkan kalimat di Langkah 1: "Kalau Redis kebetulan mati, aplikasi otomatis beralih ke penyimpanan file, jadi login tetap jalan." dan "password dicek dengan bcrypt, tidak pernah disimpan polos." Sumber: app/Core/SessionManager.php, app/Service/AuthService.php, app/Service/UserService.php, ADR-005. Fallback juga diuji langsung saat penyusunan dokumen ini (lihat A.3).

A.1 Apa itu "sesi" dan kenapa di Redis?

  • Setelah login berhasil, server menyimpan user_id, role, user_name, dan last_activity di sesi PHP. Browser hanya memegang cookie berisi ID sesi acak (iom_session) — bukan data pengguna.
  • Penyimpanan sesi default PHP adalah file di server. Aplikasi ini menggantinya ke Redis (session.save_handler=redis, alamat tcp://redis:6379?database=0) agar: (1) sesi kedaluwarsa otomatis oleh Redis (TTL), (2) cepat dibaca di tiap halaman karena di memori, (3) tidak membebani MySQL, dan (4) tidak terikat satu server/kontainer.
  • Redis dipakai untuk sesi (database 0) dan cache izin role (database 1, Lampiran B). Data bisnis (termasuk stok) tidak pernah disimpan di Redis; sesi bisa hilang tanpa merusak data — dampaknya cuma pengguna harus login ulang (ADR-005).
  • Masa berlaku: SESSION_LIFETIME = 3600 detik (default di docker-compose.yaml). Selain cookie, server juga memeriksa idle timeout: bila selisih last_activity dengan sekarang melebihi lifetime, sesi dihancurkan dan pengguna dianggap belum login (AuthService::currentUser()).
  • Cookie sesi diamankan: HttpOnly (tidak terbaca JavaScript), SameSite=Lax, dan flag Secure aktif di produksi bila lewat HTTPS (termasuk di balik reverse proxy Caddy via header X-Forwarded-Proto).
  • Saat login ID sesi diganti (session_regenerate_id(true)) untuk mencegah session fixation, dan token CSRF dibuat baru.

A.2 Bagaimana fallback "Redis mati → file" bekerja

  1. Setiap request, SessionManager::start() melakukan probe TCP singkat ke Redis (fsockopen, timeout 0,5 detik). Ini hanya cek "port terbuka?", bukan handshake Redis penuh.
  2. Bila terjangkau → sesi disimpan di Redis. Bila tidak → aplikasi menulis peringatan ke error log ("Redis unreachable … falling back to file sessions") dan memakai session.save_handler=files.
  3. Tujuannya (kode ditandai C-02): tanpa fallback, handler Redis yang mati membuat setiap request gagal atau menggantung, sehingga tak seorang pun bisa login. Dengan fallback, halaman login tetap berfungsi, pengguna bisa masuk, dan aplikasi tetap dipakai.
Batasan yang perlu diketahui (disimpulkan dari logika kode — inferensi) Pilihan handler dibuat per request dan sesi tidak dipindahkan antar penyimpanan. Akibatnya: pengguna yang sudah login lewat Redis akan terlihat "logout" saat Redis mati (sesinya ada di Redis, sementara request baru membaca file), dan harus login ulang; login baru pada masa gangguan tersimpan di file lokal kontainer dan tidak terlihat lagi setelah Redis pulih. Probe hanya mengecek TCP, jadi Redis yang port-nya terbuka tetapi macet tidak terdeteksi. Jawaban jujur saat ditanya: "login tetap bisa, tetapi sesi lama tidak ikut pindah."

A.3 Bukti verifikasi

Dijalankan saat penyusunan dokumen: SessionManager diarahkan ke Redis palsu (127.0.0.1:6399). Hasil: log "falling back to file sessions", session.save_handler=files, sesi aktif dan data sesi dapat ditulis/dibaca. Pada mode normal (Redis hidup) handler = redis. Untuk demo langsung: docker compose stop redis lalu login → tetap berhasil; docker compose start redis untuk memulihkan.

A.4 Password: bcrypt, tidak pernah polos

  • Menyimpan: saat Admin membuat user atau mengganti password, aplikasi memanggil password_hash($password, PASSWORD_BCRYPT) (UserService). Yang masuk kolom users.password_hash hanyalah hash berawalan $2y$10$… (60 karakter; $2y$ = bcrypt PHP, 10 = cost). Password asli tidak disimpan di database, sesi, maupun log. Data seed juga berisi hash, bukan teks polos.
  • Mengecek: saat login, password_verify($password, $user->passwordHash) membandingkan input dengan hash. Hash tidak dapat "dibalik" ke password; bcrypt memakai salt acak per password (tertanam dalam hash) sehingga dua user dengan password sama punya hash berbeda, dan sengaja lambat (cost 10 = 210 putaran) agar sulit ditebak massal.
  • Akun nonaktif, email tak dikenal, dan password salah menghasilkan pesan yang sama (anti user-enumeration); percobaan gagal dicatat sebagai login_failed.
  • Aturan password: minimal 6 karakter saat dibuat Admin; email unik. Tidak ada ganti password mandiri — Admin menggantinya lewat Users → Edit (My Profile hanya nama & email).
LAMPIRAN BApa yang sebenarnya di-cache Memcached
Koreksi pentingKalimat di versi sebelumnya — "sebagian data dashboard yang sering dibaca & jarang berubah dipercepat dengan cache Memcached" — tidak sesuai kode. DashboardService dan SalesDashboardService tidak memakai cache sama sekali; seluruh angka dashboard (nilai inventori, low stock, jumlah PO/SO per status, antrean) dibaca langsung dari MySQL tiap kali halaman dibuka. Kalimat itu sudah diganti di Langkah 2.

Hanya dua jenis data yang di-cache di Memcached (pola cache-aside lewat CacheService; sumber: ProductService, FileValidationService, ADR-005). Cache izin role ada di Redis (lihat kotak di bawah tabel):

Yang sengaja TIDAK di-cache

  • Stok (product_stocks) dan ketersediaan — selalu dibaca langsung dari MySQL; penjaga konsistensinya adalah transaksi + SELECT … FOR UPDATE (ADR-002), bukan cache. Alasannya agar syarat ARCH-02 (anti-oversell) tidak pernah bergantung pada data usang.
  • Dashboard, daftar produk/SO/PO, laporan, Stock Ledger — semuanya langsung dari database.

Perilaku bila Memcached mati

CacheService mengecek koneksi saat dibuat (timeout 500 ms). Jika ekstensi/ server tidak tersedia, ia menandai diri "tidak tersedia" dan semua get mengembalikan kosong, set/delete tidak melakukan apa-apa — aplikasi tetap berfungsi penuh, hanya membaca dari MySQL. Cache bukan sumber kebenaran dan tidak pernah write-through.

Redis vs Memcached — ringkas untuk tanya-jawabRedis = sesi login (butuh TTL, hilang tak merusak data). Memcached = cache baca produk & aturan validasi file; cache izin role juga di Redis (database terpisah dari sesi). Semuanya bisa dibangun ulang dari MySQL. Dipisah agar kelak tak ada yang "sekalian" menyimpan stok di store yang juga menjaga login.

  • Submit → Pending Approval; sekarang tombol Edit/Submit hilang, tombol Approve/Reject tidak ada, Cancel Order masih ada.
  • Cancel pada SO Draft/Pending milik sendiri → konfirmasi "Cancel this sales order?" → status Cancelled. Pada SO Approved/Fulfilled → tombol Cancel tidak tersedia (minta Admin).
  • Setelah Admin approve: status Approved; tidak ada tombol Issue Goods untuk Sales. Setelah Warehouse issue: Fulfilled.
  • Reports: pilih rentang tanggal → Export Orders → CSV hanya berisi pesanan Sales ini; tanggal kosong atau mulai > akhir → ditolak.
  • My Profile: ubah nama/email → sukses. Logout.

F.3 Catatan jujur untuk tanya-jawab

  • Halaman daftar Categories, Warehouses, Suppliers, dan Products hanya butuh login; Sales & Warehouse yang mengetik URL-nya melihat data read-only (tanpa tombol kelola). Yang dijaga ketat di server adalah aksi tulis. /customers dijaga customers.view (Warehouse → 403).
  • Menu disembunyikan lewat PermissionService (yang di-cache 1 jam di Redis); guard server memakai data izin yang sama. Perubahan izin di database dapat tertunda hingga TTL habis.
  • Menandai inferensi = disimpulkan dari pembacaan kode, belum dijalankan end-to-end.
