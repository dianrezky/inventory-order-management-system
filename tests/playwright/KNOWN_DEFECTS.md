# IOMS E2E — Known Defects, Spec/Code Mismatches & Unresolved Decisions

> **Post-merge correction (read first):** between this suite's original research
> pass and this commit, `origin/master` gained a new DB-backed upload validator
> (`app/Service/FileSignatureValidator.php` + `FileValidationService` +
> `file_validation_rules` table, seeded in `database/seed.sql`). It changes
> upload behaviour the original design spec (and an earlier draft found in
> `docs/superpowers/specs/2026-10-04-deep-e2e-suite-design.md`, written in
> parallel) both assumed: **a file's extension is now checked FIRST, and its
> magic-byte signature is validated against THAT extension's rule** — so a
> real PNG renamed `.jpg` is now **rejected** (`MESSAGE_SIGNATURE_MISMATCH`),
> not silently accepted as "extension is ignored" (the old, now-stale,
> `ImageUploadService`-only behaviour). `support/files.ts`/`support/messages.ts`
> have already been updated to the verified-current behaviour; this note
> exists so nobody re-introduces the stale assumption from an earlier reading
> of this repo or of chat history. There is also a brand-new double-extension
> guard (`evil.php.jpg` → `MESSAGE_DOUBLE_EXTENSION`) with its own fixture
> (`fixtures/files/double-extension.php.jpg`). None of this is a defect — it
> is a real security improvement that landed mid-task; it is recorded here
> only because it invalidates a specific, previously-documented assumption.

Classification taxonomy (per approved decision on this task):
`EXPECTED_BEHAVIOR` — current code is intentionally correct; asserted normally.
`KNOWN_DEFECT` — current code is wrong; the suite documents/reproduces it but the *regression contract* represents the **correct intended behaviour**, not the bug.
`SPEC_CODE_MISMATCH` — source evidence (service/UI/schema/tests/docs) disagrees with itself; authoritative rule not yet determined from the repo alone.
`TEST_BLOCKER` — prevents writing a correct test at all (none identified yet).

Every row below is tagged `@quirk` in its regression spec (once written) and never used to justify a passing assertion on the broken behaviour itself.

## Classified as `EXPECTED_BEHAVIOR` (not defects — recorded here only because they look surprising at first read)

- **Stock Ledger has no date filter and no stored before/after columns.** The "Before → After" column is a server-computed running `SUM(qty)` (correlated subquery in `StockLedgerMySQLRepository::findFiltered()`), confirmed live (DB oracle smoke test: `stockOf()` == `ledgerSum()` on pristine seed). This is simply how the feature is built, not a bug — see `FOUNDATION_CONTRACT.md` §6 for the arithmetic contract.
- **Profile has no password field and does not expose role as editable.** `ProfileController`/`UserService::updateProfile()` only accept name+email; this is the intended, narrower scope of self-service profile editing vs. admin-driven `UserController`.
- **`GET /logout` is a no-op (404).** The only supported logout path is `POST /logout` with CSRF (`routes.php`). The suite never treats the legacy GET form as a valid logout path; at most one security regression test confirms the unsupported method mutates nothing.
- **Notifications have no per-user read state** (`read_at` is a single column on the `notifications` table, not a join table) — `mark-all-read` is genuinely global. This drives the `exclusive`-project placement for notification specs, not a defect to fix.
- **SalesDashboardService anchors "today/week/month" to `Asia/Jakarta`**, while the rest of the app (and MySQL `CURDATE()`) uses UTC. This is a real source of test flakiness risk near Jakarta-midnight boundaries, not a defect — flagged for Agent 6/Agent 7 to design around (mock the clock or avoid boundary-sensitive assertions), not to "fix" in the app.
